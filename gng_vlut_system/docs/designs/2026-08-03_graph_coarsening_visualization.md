# 設計書案 - エフェクティビティマップのグラフ縮約可視化

- 作成: 2026-08-03
- 状態: **案**(未承認・未実装)
- 関連: [TASK_LIST.md](../TASK_LIST.md) デモ可視化 A〜E / [TASK_CANDIDATES.md](../TASK_CANDIDATES.md) 階層構造

---

## 1. 目的

エフェクティビティマップ(`offline_urdf_trainer` が生成する GNG グラフ + Voxel-LUT)を、**先方への提示に耐える形**で可視化する。

判断基準はデバッグ用途とは異なり、**分かりやすさと印象への残りやすさ**を優先する。精度より可読性を採る。

## 2. 背景と問題

### 2.1 現状

ノードは `Status` に20以上の属性を持つが、ビューア側の配色は `'label' | 'uniform'` のみ(`gngGraphics.ts`)で、状態も指標もほぼ反映されていない。

### 2.2 解決したい問題

**手先位置が重複または近接するノードが多く、色が混ざってまだらになる。**

原因は冗長性である。`weight_coord` は手先位置なので、同じ手先位置を実現する異なる関節配置のノードが同一点に積み重なる。そこに安全・危険・衝突が混在すると、描画順で色が入れ替わる。

派生して、**回転させると点の前後関係が入れ替わってちらつく**。デモで最も印象を損なう現象である。

### 2.3 問題の本質

「1マーク = 1ノード」という前提が崩れている。配色を変えても解決しない。**描画単位を変える**必要がある。

## 3. 要件

| # | 要件 | 理由 |
|---|---|---|
| R1 | 1つの視覚マークに複数ノードが重ならない | 混色とちらつきの解消 |
| R2 | **位相構造(エッジ)が見える** | 位相地図であることが手法の看板。ここを消すと単なるオキュパンシーグリッドになる |
| R3 | 学習されたノード位置の不規則性が残る | 一様格子に見えると R2 が伝わらない |
| R4 | 非一様な密度が伝わる | GNG が学習した粗密の情報 |
| R5 | 3値状態が説明なしで読める | 先方向け。緑=使える / 黄=注意 / 赤=使えない |
| R6 | 粒度を可視化専用の要件に固定しない | 別用途(階層プランニング等)で基準が変わる |

## 4. 方式

**coord エッジに沿ったグラフ縮約により集約する。**

集約ノードは元ノードの代表ではなく、束ねた集合を要約する新しい実体とする。

### 4.1 却下した案と理由

| 案 | 却下理由 |
|---|---|
| **ボクセル格子で集約** | 位相構造が消えて単なるオキュパンシーグリッドになる(R2違反)。格子隣接は実際の到達可能性を反映しない |
| **格子で集約しエッジだけ継承** | ノード位置が格子中心になり「ボクセルに線を引いただけ」に見える(R3違反) |
| **束ねた中の代表ノードを選出** | 集約ではない。位置以外の属性も集約すべき |
| **worst-wins による状態集約** | §4.4 参照 |
| **`is_surface` による外殻表示** | 当該フラグは未使用かつ当面使う予定がない。別用途(複数ロボットの作業空間の重なり)のため温存 |

### 4.2 縮約アルゴリズム

```
入力: ノード集合 V, coord エッジ集合 E_coord, 目標ノード数 k
出力: 集約ノード集合 V', 集約エッジ集合 E', マージ列 M

1. E_coord を長さ(両端の weight_coord 間のユークリッド距離)の昇順にソート
2. union-find を初期化(各ノードが独立した集合)
3. 集合数 > k である間、短い順にエッジ (u,v) を取り:
     find(u) != find(v) ならば union し、マージ列 M に記録
4. 各集合について集約属性を計算(§4.3)
5. 元エッジ (u,v) のうち find(u) != find(v) のものを集約エッジとする(重複排除)
```

計算量は `O(|E| log |E|)`(ソート律速)。5,500ノード規模なら十分高速。

**coord エッジを使う理由**: 手先位置空間の近傍を結んでいるため、縮約すると重なっているノード同士が優先的に潰れる。混色の原因に直接効く。

### 4.3 集約ノードの属性

| 属性 | 集約規則 |
|---|---|
| 位置 | メンバの `weight_coord` の**重心** |
| 元ノード数 | メンバ数 |
| 状態 | **best-wins**(§4.4) |
| 可操作性 | メンバ中の最良値(表示は任意) |
| メンバID列 | 詳細パネル用に保持 |

重心は実在する姿勢に対応しないが、集約ノードはそもそも姿勢ではなく要約なので問題ない。格子中心と違い、実際にノードが存在する位置に寄るため分布が素直に残る(R3)。

### 4.4 状態の集約は best-wins

状態の優先順位を `safe > danger > colliding` とし、**メンバ中で最も良い状態**を採る。

| 集約結果 | 条件 |
|---|---|
| safe | メンバに1つでも安全な姿勢がある |
| danger | 安全はないが危険帯なら通れる姿勢がある |
| colliding | メンバの全姿勢が衝突 |

判定は `is_colliding` / `is_danger` から導く。

**worst-wins を採らない理由**:

worst-wins が答えるのは「その場所の**全ての**姿勢が安全か」であり、誰もその問いを立てない。実際に知りたいのは「その場所に安全に手を届かせられるか」であり、プランナは安全な姿勢が1つあればそこを使える。

特に**把持対象の近傍**では対象に接触する姿勢が必ず含まれるため worst-wins だと赤になるが、有効な接近姿勢は存在する。「赤いのに掴みに行く」という矛盾した絵になり、先方に突っ込まれる。

best-wins はプランナのゴール候補選定とも基準が一致する。

```cpp
// topological_map_avoidance_node.cpp
if (node.id != -1 && node.status.active && node.status.valid &&
    !node.status.is_colliding) {
    cached_safe_goal_ids_.push_back(node.id);
}
```

可視化が赤と言う場所をプランナが使う、という自己矛盾を避けられる。

### 4.5 マージ列による多階層化

縮約時にマージ順を記録すれば、**任意のノード数で打ち切って任意レベルのグラフを再構成できる**。縮約は1回で済み、レベル切り替えに再計算が不要になる。

記録形式は 1マージあたり `(集合A, 集合B, 統合後ID, その時点の集合数)`。

これは [TASK_CANDIDATES.md](../TASK_CANDIDATES.md) の階層構造の議論にも接続する。

### 4.6 粒度は引数

目標ノード数は呼び出し側が与える。可視化は「画面で見やすい数」を、他用途はそれぞれの基準を渡す(R6)。

想定される他用途: 階層プランニング(探索効率)、通信量削減(帯域)、協調動作エリアの抽出(空間分解能)。

## 5. 配置

**C++ core に汎用関数として実装する。**

| | フロントエンド(TS) | C++ core |
|---|---|---|
| 実装コスト | 低い | やや高い |
| プランニングからの再利用 | 不可 | **可** |
| 通信量 | 全ノード送信 | **集約済みを送信** |

§4.6 の通り他用途が見えているため、core に置いて作り直しを避ける。ビューアへは集約済みを配信するので通信量も減る。

## 6. 描画仕様

### 6.1 マーク

| 要素 | 表現 |
|---|---|
| 集約ノード | 球。半径は元ノード数の単調増加関数(R4) |
| 集約エッジ | 線。**格子隣接からは引かず**、元の GNG エッジを継承(R2) |

### 6.2 配色

3値は系列色ではなく**状態色**として扱う。意味が予約されており、`topology_group_id` のような識別用途と混ぜてはならない。

| 状態 | hex | 意味 |
|---|---|---|
| safe | `#0ca30c` | 安全に動かせる |
| danger | `#fab219` | 注意が必要 |
| colliding | `#d03b3b` | 動かせない |

**状態色は色だけに頼らせない。凡例とラベルを必ず添える。** 明色面上では danger がコントラスト比 1.79 と低く、色単独では判別を保証できないため。

なお 3D 散布では任意の2点が隣接しうるため、カテゴリ色は実測で**3色までしか判別できない**(4色で通常視の識別下限を割る)。`topology_group_id` を色分けする設計は群が4つ以上あると原理的に読めないので採らない。

### 6.3 将来の拡張

余裕の情報が必要になった場合、色相=3値、明度=安全率(そのボクセルで安全な姿勢が取れる割合)の二層にできる。第一版では採らない。

## 7. 実装の段階

| 段階 | 内容 | 完了条件 |
|---|---|---|
| A | C++ core にグラフ縮約を実装(マージ列保存を含む) | 任意粒度のグラフを即座に取り出せる |
| B | 集約結果のビューアへの配信 | 既存 `topofuzzy_bridge` / `gng_viewer_bridge` 経由で届く |
| C | ビューア側の描画 | 混色とちらつきが解消し、位相構造が見える |
| D | 粒度スライダ | マージ列から再計算なしで切り替わる |
| E | (余力) 障害物での塗り替え | ノードが赤くなり、**エッジが切れる** |

### 段階Eについて

障害物によってグラフの接続が切断される絵は、**オキュパンシーグリッドでは表現できない**。「そこを通れなくなった」が構造として見えるため、位相地図を使う理由がそのまま伝わる。障害物が動く現場(ゴミ処理場)は先方の関心にも直結する。

VLUT の逆引きが既にあるため、仕組みとしては動くはずである。

## 8. 未確認事項

- **ビューアがどちらの腕の手先位置を描いているか。** `refresh_coord_weights` は `coord_layer_index == 0` のときだけ `weight_coord` を更新するため、双腕なのに片腕分しか描いていない可能性がある。両腕のノードが同じ配列に混在しているなら、それ自体が重なりの一因になりうる。**段階Aの前に確認する。**
- 目標ノード数の具体値。実際に描画して決める。

## 9. 検証

- 集約前後でノード数が目標値に一致すること
- 集約エッジに自己ループが含まれないこと
- マージ列から再構成したグラフが、その粒度で直接縮約した結果と一致すること
- 回転させてちらつきが出ないこと(目視)
- 把持対象の近傍が赤にならないこと(§4.4 の妥当性確認)
