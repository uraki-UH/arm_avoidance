# リリースノートの書式

変更の結果と検証範囲を、原則として次の2節で記載。

```md
# YYYY-MM-DD - 対象と変更結果

## 1. 要約

何がどう変わったかを1〜2文で記載。

- 主な変更・採用した方式
- 効果と、採用を見送った案があればその理由

## 2. 条件・検証

| 項目 | 内容 |
| --- | --- |
| 影響 | 変更した挙動・設定・入出力・互換性 |
| 条件 | 入力、設定、計測対象 |
| 結果 | 確認できたこと・未検証の範囲 |

根拠・再現手順：既存の仕様・計測資料へのリンク。
```

## 書き方のルール

- 報告は40〜80行を目安に、要点・結果・必要な条件へ限定。短い変更はさらに簡潔に記載。
- 「追加なし」「変更なし」のためだけの見出しは不要。検証や条件を省くための行数合わせも不要。
- 同じ作業の追加修正は既存ノートへ統合。独立した変更だけ別ファイルへ記録。
- topic・parameter・message・launch引数を変更した場合は、最終値と必要な移行方法を記載。
- 数値には対象・単位・比較条件を併記。区間と全体、実測と推定、当時の結果と現行仕様を区別。
- 検証コマンドは再現資料を正本とし、報告には参照リンク。正本がない場合のみ必要なコマンドを本文へ記載。
- 起動した試験プロセスの終了状況と、失敗・未検証・互換性上の制約を保持。
- `progress.md`は1件2〜3項目の実施事実・結果・根拠リンク。仕様・手順・同じ数値表の再掲は不要。

## まとめ版の書き方

複数のノートをまとめる場合も「要約」「条件・検証」を基本とし、到達点を表や短い箇条書きで整理。
途中の修正経緯と重複する詳細は省き、必要な仕様・再現手順を既存の正本へリンク。
古い報告には対象日を記載し、当時の未実装事項を現在の未完了タスクとして転記しない。
