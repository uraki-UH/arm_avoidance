# プロジェクト文書の維持

記録先は `gng_vlut_system/docs/`。予定と実績、提案と確定仕様を混在させない。

## 記録先

| 内容 | 正本 |
| --- | --- |
| 実際に行った変更・調査・検証とその結果 | `progress.md` |
| 取り組む意向はあるが時間・依存作業などの都合で保留中 | `pending.md` |
| 却下・不採用・採用見送りの判断と理由 | `reject.md` |
| 実行順が確定した未完了作業 | `TASK_LIST.md` |
| 方針未確定の残課題 | `TASK_CANDIDATES.md` |
| 比較案や詳しい設計検討 | `designs/` の関連文書 |
| 現行実装の仕様と制限 | `TECHNICAL_SPEC.md` または対象パッケージの仕様文書 |
| 利用者に影響する挙動・互換性の変更 | `releases/` |

## 進捗・保留・不採用の区別

- `progress.md` は日付・対象・実施内容・結果・根拠へのリンクだけを記録。予定、提案、未着手のTODOは記載しない。
- 失敗した検証も実施事実として記録。ビルド成功を実動作成功と扱わず、未検証の範囲を明示する。
- `reject.md` は日付・対象範囲・判断（不採用／採用見送り）・判断者または根拠・理由・再検討条件を記録。単なるテスト失敗や未実装は不採用とみなさない。
- 採用する意向はあるが今は進めない作業は `pending.md`。採用・方式自体が未確定なら `TASK_CANDIDATES.md`。方式を採用しない判断は `reject.md` とし、時間不足だけを却下理由にしない。
- 保留記録は保留日・対象・理由と根拠・完了済み範囲・再開条件・次の一手を記載。期限や再開条件が未定なら未定とし、架空の約束を補わない。
- ユーザーの指示とエージェントの提案を区別。ユーザーが決めていない却下理由や恒久禁止を補わない。
- 関連作業の開始時に対象語で `reject.md` と `pending.md` を検索。見送り案の再実装や保留作業の再開は、判断根拠・再開条件を確認した範囲だけ。再採用が明示された場合は過去の不採用判断を消さず、新判断へのリンクを追記する。
- 保留・再開が決まったら `TASK_LIST.md` と `pending.md` の間で未完了作業を移管。元の台帳には必要な場合だけ参照リンクを残し、本文の二重管理を避ける。実施済み範囲は進捗記録へのリンクで保持。
- 方針再検討への移管先は `TASK_CANDIDATES.md`、不採用判断への移管先は `reject.md`。更新が途絶えただけの既存タスクを勝手に保留へ移さない。
- 進捗には詳細な仕様を複製せず正本へリンク。全ファイルへの機械的な追記や、同じ全文の多重保存は不要。
- 過去の会話から作業履歴を一括生成しない。既存記録の移動は依頼範囲だけとし、既存ファイル・リンクを無断削除しない。

## 作業手順

1. 文書を読む前に、`rg` で該当見出しや記号を先に探す。
2. 編集直前に、対象ファイルの現状を必ず読み直す。
3. 手作業で入った変更を守り、最小限の差分だけ当てる。
4. 上表から関係する正本だけを更新。利用者向けの挙動変更は `RELEASE_NOTE_TEMPLATE.md` に沿ってリリースノートを追加。文書・スキル整理だけなら進捗記録で十分。
5. 候補が実装済みになったら、仕様やリリースノートを先に整えたうえで、その候補だけを削除する。
6. 最終差分を見直し、ユーザーが消した文や書き換えた文を戻さない。

## `TASK_LIST.md` は手作業で管理する

ユーザーは `gng_vlut_system/docs/TASK_LIST.md` を自由に直接編集する。追加、並べ替え、削除はこの作業フローの外でもいつでも行われる。ここでは `[[preserve-user-edits]]` の考え方をこのファイルに適用する。

- 現在ディスク上にある内容を正とみなし、想定より少なくても並び順が変わっていても、そのまま受け入れる。
- ユーザーが消した項目は、前回の作業で追加したものでも戻さない。
- 完了扱いで項目を削除するのは、実装確認と、それに対応する `TECHNICAL_SPEC.md` またはリリースノート更新が済んだ後だけ。判断に基づく保留・再検討への移管は、内容を移管先へ保持したうえで実施する。
- 作業途中でそのタスクが再び未確定になったら、消さずに `TASK_CANDIDATES.md` へ戻す。

## 未確定の評価指標

- 測定対象・単位・計算根拠・利用先が未確定な指標へ、体裁を整えるだけの計算式を追加しない。
- 未計算は既存インターフェースの無効値表現（NaN、valid=false、nullなど）に従い、0や成功スコアで代用しない。
- 暫定式を削除する前に選択・制約判定・可視化・保存の利用箇所を確認。実際に候補順序や採否を変える場合は影響を説明し、対象が曖昧なら確認する。
- 設計案には未確定と明示し、進捗や仕様へ計算済みと記載しない。
