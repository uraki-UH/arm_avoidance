# プロジェクト文書の維持

文書は作業日誌ではなく、現行仕様・利用手順・後続判断のための正本。対象パッケージのREADME・仕様書を優先し、必要な作業記録は `gng_vlut_system/docs/` へ集約。

## 更新するかの判断

- 通常の編集・実験・修正途中では正式文書を更新しない。経過・一時的な失敗は会話で報告し、必要な生ログは試験用の一時領域へ保存。試行ごとのMarkdownを生成しない。
- 採用した実装と検証結果が確定した時点で、既存の仕様・使い方・設定・互換性の記述が古くなる場合だけ該当箇所を更新。会話の返信回数や編集回数を更新の単位にしない。
- 新規の作業報告書・日付別リリースノートは明示依頼時のみ。必要な仕様・手順の正本が存在しない場合は新設可能だが、試行履歴を混在させない。
- `progress.md` は自動追記しない。明示依頼、または引継ぎに必要な確定結果がある場合だけ短く記録。READMEを更新した事実や規約を変更した事実だけの追記は不要。
- 不採用・保留の台帳は、長期的な判断・再開に必要な場合のみ更新。一時的な失敗・案の変更を毎回登録しない。既存台帳を今回の作業で解消した場合は該当項目を整合させる。
- 文書化の許可確認を通常作業に挟まない。この判断基準とユーザーの指示で必要な更新を選ぶ。
- 過去文書の一括整理・削除は依頼範囲のみ。現行仕様の更新では古い記述を置き換え、続報の追記で履歴を積み上げない。

## 報告・表の表現

- 列挙可能な情報は「項目名: 値」。数量の値は数値と単位だけとし、「統合」などの操作・理由は別項目。例：`設定項目数: 5 個 → 2 個`。定性的な値は状態語・識別子、説明の補足は体言止め。文章化のためだけの「〜した」「〜する」は不要。
- 変更内容・測定結果・評価を分離。測定値には単位と比較条件を付記。短縮や件数減少だけを根拠に、読みやすさ・品質・効率の改善を断定しない。
- 表は同じ種類の情報を同じ列へ配置。数量比較は指標・変更前・変更後・差分・条件から必要な列だけ選択し、数値セルに「高速化」「改善」などの評価語を混在させない。共通単位は列名・指標名への集約も可。
- 理由・比較条件・制限は別項目で短く補足。未測定・未検証・対象外を区別し、空欄や0で代用しない。引用・コマンド・識別子・APIの値は原表記を保持。詳細な書式は[テンプレート](../../gng_vlut_system/docs/RELEASE_NOTE_TEMPLATE.md)を参照。

## 記録先

以下は、上記基準で記録が必要と判断した場合の振り分け。全ファイルを更新するチェックリストではない。

| 内容 | 正本 |
| --- | --- |
| 実施済みの変更・調査・検証結果 | `progress.md` |
| 実施する意向はあるが時間・依存作業などで保留中 | `pending.md` |
| 不採用・採用見送りの判断と理由 | `reject.md` |
| 実行順が確定した未完了作業 | `TASK_LIST.md` |
| 方針未確定の残課題 | `TASK_CANDIDATES.md` |
| 比較案や詳しい設計検討 | `designs/` の関連文書 |
| 現行実装の仕様と制限 | `TECHNICAL_SPEC.md` または対象パッケージの仕様文書 |
| 利用者に影響する挙動・互換性の変更 | `releases/` |

## 更新手順

1. 対象語で関係する文書と `reject.md`・`pending.md` を検索し、該当箇所だけ確認。見送り・保留の根拠と再開条件を尊重。
2. 編集直前の内容と差分を確認し、ユーザーの削除・並び順を保持。記憶や過去の会話から履歴を復元しない。
3. 採用済みの最終状態を必要な正本へ反映。既存の仕様・操作手順で足りる場合は報告書を追加しない。明示依頼で報告を作る場合のみ[短い書式](../../gng_vlut_system/docs/RELEASE_NOTE_TEMPLATE.md)を使用。
4. 進捗記録が必要な場合のみ、日付・対象・確定結果を1〜2項目で記載。詳細は正本へリンクし、仕様・数値表・手順を重複させない。
5. 差分で事実・条件・制限の欠落と重複を確認。参照先が存在し、必要な根拠が残ることを確認。短縮率だけを品質の代わりにしない。

## 状態と履歴の保持

- 残す結果は実績のみ。未解決の失敗、未検証、結論の信頼性を左右する条件は保持し、ビルド成功を実動作成功と扱わない。修正済みの一時エラーや、最終判断に無関係な試行履歴は省略。
- 不採用は日付・対象・判断・判断者または根拠・理由・再検討条件を保持。テスト失敗・未実装・時間不足だけを不採用とみなさない。ユーザー未決定の禁止を補わない。
- 保留は日付・対象・理由と根拠・完了済み範囲・再開条件・次の一手を保持。期限や条件の未定は未定のまま記載。
- `TASK_LIST.md` は手編集を優先。完了による削除は実装確認と仕様またはリリースノートの更新後だけ。方針が未確定に戻った作業は `TASK_CANDIDATES.md` へ移管。
- 保留・再開の決定時のみ `TASK_LIST.md` と `pending.md` 間で移管。不採用への移管先は `reject.md`。移管先に内容を保持し、元の台帳には必要なリンクだけ残す。更新停止だけで保留へ移さない。
- ユーザー指示とエージェント提案を区別。再採用が明示された場合も過去の不採用判断を残して新判断へリンク。依頼外の記録移動・ファイル削除・リンク削除は行わない。

## 未確定の評価指標

- 測定対象・単位・計算根拠・利用先が未確定な指標へ、体裁を整えるだけの計算式を追加しない。
- 未計算は既存インターフェースの無効値表現（NaN、valid=false、nullなど）に従い、0や成功スコアで代用しない。
- 暫定式を削除する前に選択・制約判定・可視化・保存の利用箇所を確認。実際に候補順序や採否を変える場合は影響を説明し、対象が曖昧なら確認する。
- 設計案には未確定と明示し、進捗や仕様へ計算済みと記載しない。
