# 時間見積もりと長時間実行の条件

対象は長い実験・夜間実行・締切付きの探索。ユーザーの追加指示なしで、許可済みの仕事を完了条件または停止条件まで継続。時間を埋めるためだけの実験追加は不要。スキル整備・計画・見積もりだけの依頼では実験を開始しない。

## 実行前の契約

以下をユーザーの指示と既存設定から整理。不足情報のうち実行判断に必須なものだけ質問し、回答待ちの間は独立した準備を継続。

- 目的、成果物、合格基準、品質を維持する条件。
- 対象コード・データ・設定・変更可能範囲、既存の手編集。
- 終了日時または最大経過時間、試行数・一試行の上限、失敗時の扱い。
- CPU・GPU・メモリ・ディスク・同時実行数の制約と、他の実験との競合。
- 許可済みの実験・修正・再ビルド・再試行と、承認が必要な未許可操作。
- 結果の保存先、途中経過、再開方法、今回起動するプロセスの所有情報。

無人実行で終了日時も有限の実行範囲もない場合は、実験開始前に上限を確定。「夜通し」だけから無制限の反復を推測しない。日時はユーザーのタイムゾーンを使用。本環境ではAsia/Tokyo。日付を含む絶対日時とUTCオフセットへ解決して伝達。「朝7時」の対象日が文脈で確定できない場合は確認。相対時間の計測は単調時計を基本とし、再開時に絶対締切を再評価。

トークン・金額の上限は明示された値だけを採用。未知のusageをゼロ扱いしない。単なる実験依頼からGoalや別モデル・別AI呼出しの利用予算を推測しない。

## 継続方法の選択

- 既定の試験一覧を回す仕事: [run-benchmark-batch](../../run-benchmark-batch/SKILL.md)のrunner。計測・終了・ログ保存をプロセス側へ担当。
- 結果に応じて次の実験や修正を選ぶ仕事: 主担当が判断し、許可済みの範囲で有限の実験単位を追加。必要な独立調査・レビューだけを委任。
- ユーザーがGoalまたは`/goal`を明示的に依頼した場合: 利用可能なGoal機能を使用。完了条件・停止条件と証拠を維持。予算上限への到達は目標達成ではない。

現在の会話・実行セッションの継続と、会話終了後の自動再開は別の仕組み。スキルやrunnerだけでCodexを再起動する保証はない。自動継続機能が利用できない場合はその制約を伝達し、有限のバッチと再開可能な記録を用意。無人稼働という表現だけでcron・systemd・通知サービス・別Codex呼出しを追加しない。

## 見積もりと実験選択

調査・実装・初回ビルド・データ準備・実験・集計・終了確認を分離。初回は幅と根拠を提示し、未測定を確定値に見せない。初回の短い試行や過去の同条件ログで更新。既に信頼できる実測があれば見積もり目的だけの追加試行は不要。

逐次実験の概算は、準備時間 + 条件別の一試行時間×残り試行数 + 集計・検証・終了処理の予約時間。並列実験は依存経路と共有資源の競合を考慮し、単純に担当数で割らない。

平均を中心値に、観測されたばらつき・初回初期化・余裕を加えた幅を提示。少数試行から精密な確率区間を主張しない。runnerが出す残り予測は実験分であり、主担当の調査・集計・後片付けは別枠。予測と強制上限は別の値。

締切から集計・停止・確認の時間を先に確保。予約時間の根拠がない場合は仮定を明示。新しい実験の予測上限が残り実験枠を超える場合は、反復数・条件数を削減するか、その試行を開始しない。追加候補は情報価値・品質確認・残り時間から選択。比較条件や品質基準を時間合わせのために緩めない。

準備・ビルドなどrunner外の長いコマンドも、残り枠に収まる有限のタイムアウトで実行。実験開始前の準備を無制限にしない。

runnerの`--timeout-sec`と`--max-total-sec`に有限値を指定。バッチを追加するたび、現在時刻から実験終了予定までの残り枠で全体上限を更新。一試行上限も全体の残り枠に収める。準備や再ビルドが予定を超えた場合は実験数を減らし、当初の全試行数を強行しない。

## 待機と判断の節目

起動は継続可能な実行セッションで管理し、開始時に見積もり・終了予定・保存先を伝達。通常は完了イベントと待機ツールを使用。本環境では一回のブロッキング待機は60秒以内。待機中の新しい指示・停止・期限変更を取り込み、終了処理へ反映。

試行完了、失敗、予測の大きなずれ、資源制限、実験群の区切りを判断の節目にする。同じログやPIDの高頻度取得だけのモニターは不要。モニター役は判断が必要な節目で呼出し、ログ・指標・残り枠だけを渡す。ユーザーが担当や頻度を明示した場合は、その指定を優先。

## 保存と再開

新規の結果ディレクトリに、試行ごとのコマンド・条件・seed・入力データとコードの識別情報、開始終了時刻、終了コード、ログ、品質・性能指標を保存。集計値だけでなく生ログも保持。

runnerの`report.json`・`events.jsonl`を計算結果の正本とし、判断ループがある場合だけ、同じ結果ディレクトリに再開用の状態を追加。内容は目的・制約・絶対締切・完了試行・実行中試行・未実行一覧・採否・次の一手・プロセスの所有情報。試行終了などの節目で更新。未検証の候補を採用済みにしない。

再開時は締切・コード・データ・設定・既存プロセスの現在状態を確認。保存PIDだけを信用せず、開始時刻・コマンド・コンテナ・マーカーも照合してPID再利用を除外。実行中か完了済みか不明な試行を即座に二重起動しない。照合後も状態が確定しない試行は「未確定」として保留し、証拠またはユーザーの判断で再試行の可否を確定。独立した許可済み試行は残り枠内で継続可能。

現runnerには既存出力への再開オプションなし。未実行分だけの新規manifestと新規出力先で継続し、元の試行ID・条件・seedとの対応を保存。部分完了を成功扱いしない。コードやデータの変更時は別条件として記録し、異なる条件の結果を同一比較に混ぜない。再試行は合意済みの上限内に限定。

## 終了条件と片付け

完了、締切または資源上限、明示停止、繰り返す失敗、許可範囲外の操作が必要になった場合に新規試行を停止。未許可操作が必要なときは、その操作だけ保留し、残り枠で独立した許可済み作業と結果保存を完了。

停止は今回のrunner・子プロセス・プロセスグループだけ。Dockerではコンテナ内runnerの終了を確認し、ホストのdocker exec終了だけで片付け完了としない。既存ROSノード・既存コンテナの停止や再起動は明示許可がある場合だけ。ROS・Dockerなどの試験には利用可能な[restore-runtime-after-tests](../../restore-runtime-after-tests/SKILL.md)を併用。

最終報告は、目的への到達状態、実行・失敗・未実行の件数、品質と性能、予測と実時間、採用候補、保存先、再開の次の一手、起動コマンドと停止確認。実験プロセスの終了と、目標の達成を区別。PCの停止・スリープ・接続断・実行枠制限での継続や片付けは保証せず、発生した制約を記録。

本資料は長時間運用の判断条件。Goalの自動有効化、runnerの自動再開機能、OSのスリープ設定変更、夜間実験の実行を追加するものではない。
